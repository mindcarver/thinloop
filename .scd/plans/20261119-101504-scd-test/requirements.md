# 需求与验收

用户先要求独立划出测试能力，随后要求先创建技能。首版提供「设计测试」「执行验收」两种用法，可独立以自然语言或 `scd-test` 调用。明确要改产品或持久测试代码的请求由现有批准的开发流程处理。QuickDev 的自动调度接入作为后续独立选择。

| ID | 可观察验收 |
| --- | --- |
| A1 | 从用户提供的原始要求、精确批准版本和现有验收 ID 推导起始状态、动作、可见结果、反例与验证方式。能指出被缩小或缺失的要求；待确认的实质产品决定单独列出。轻量任务只留必要场景。 |
| A2 | 验收者从同一批准基线核对当前目标及完整差异。候选更改了测试也须按批准预期实测。正确候选有直接证据时判 PASS；自动创建会话与已批准的显式创建冲突时判 FAIL；流式界面没有执行或证据不匹配版本时保持 BLOCKED。观察到的违背与缺证项分别可审计。 |
| A3 | 变更由当前 Thinloop 安装契约发现。ZCode、Claude Code、Codex 已安装端核对 15 个技能及各自支持的 Hook；其他已安装端按现行支持边界验收。 |
| A4 | 仓库 CI、独立验收和合并后的精确版本检查符合 QuickDev 交付契约。 |

用户要求、批准行为与验证方式分层保存。开发者可以修复测试的环境和定位方式，改变产品预期须沿用已有的审批与追溯规则。证据记录到管理当前交付的 Issue，手工审查交付独立报告。例子和评测使用独立合成数据。
