# 需求与验收

用户要求在 QuickDev 的关键行为变更开工前根据原始要求设计测试，在合并前由独立验收者使用 `scd-test`，用一次旧验收断言被改成接受回退的历史案例实测是否拦截。

| ID | 可观察验收 |
| --- | --- |
| A1 | 关键行为的计划在产品代码变更前实际调用或加载 `scd-test` 设计模式，从原始要求、批准版本及已有验收 ID 得到起始状态、动作、可见结果和反例。测试方案加入同一份现有计划并按精确版本批准。小范围文档及纯内部无行为改动沿用聚焦验证。 |
| A2 | QuickDev 现有的新上下文独立验收者实际使用 `scd-test`，亲读原要求和批准预期、Issue、完整差异以及候选目标。它独立跑出相关证据并把结论对应到验收项。已观察到回退为 FAIL，缺少必需证据为 BLOCKED。只有当前版本的直接 PASS 以及原有门槛齐备才可以合并。 |
| A3 | 复跑真实历史基线、候选和冻结断言，验证原生相关测试可通过而原始行为已违反。再用保留相同无会话发送语义的合成候选，在真实 ZCode 中执行 QuickDev，验证合并流程实际取到独立 FAIL、没有调用合并且隔离主分支未前进。正例通过独立验收并进入允许合并路径，区分总是拒绝与正确拦截。 |
| A4 | 现有构建和全套检查通过，独立验收精确候选，普通 merge 保留获批历史。已安装宿主按现有方式刷新和验收。 |

关键行为包括用户可见成功或失败路径、已有验收语义或硬约束、对外接口、持久状态和跨层接线。测试断言如果改变这些已批准预期，也属于关键行为。已有合适的批准场景直接复用。必要的产品取舍仍走原有澄清规则。

从当前证据看，同一个历史候选的修改后测试退出 0，冻结的原始验收断言退出 1。独立调用公开入口也观察到，基线拒绝无会话发送且不创建会话，候选创建会话并发送。隔离合成场景保留这个差别，验收时不把历史案件的私有会话或真实环境放入评测。
