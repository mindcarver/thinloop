# SCD 测试设计与独立验收

开始执行前必须先读取并遵守[步骤沟通](../scd-quickdev/references/step-communication.md)。直接调用本技能也适用。

从用户要求、仓库说明、已批准计划和 Issue 找出验收依据，保留原始要求、验收 ID 与精确获批版本；若 Issue/实现缩小或改变已确认要求，核查对应新批准，不从当前代码或测试倒推预期。

## 按请求选择用法

| 请求 | 行动 |
| --- | --- |
| 设计测试、制定回归场景或检查验收项是否可测 | 读取[测试设计](references/test-design.md)，按 `P0`/`P1`/`P2` 交付起始状态、操作、可观察结果、关键反例、条件触发式 NFR 与验证方式；对 `P0` 新行为和缺陷修复执行先红后绿 ATDD（Red Mode）。 |
| 验收功能、检查 PR 是否符合原要求或核对已有测试证据 | 读取[独立验收](references/acceptance-audit.md)，按 Blind-First（先盲验、后对账）两步顺序核对差异，执行 `test-review` 5 条反模式门禁与直接验证，汇总 `PASS`、`FAIL` 或 `BLOCKED`（受控单项 `WAIVED` 仅限非 `P0`、非高风险门且已获用户显式批准的外部不可测项）。 |

## 风险分层与先红后绿 ATDD

- **`P0`（核心契约、权限、数据一致性、不可逆路径）**：必须有独立反例、先红后绿 ATDD 与强制独立新上下文子 Agent 复跑；严禁 `WAIVED`。
- **`P1`（主要业务流程与失败恢复）**：常规验收矩阵与自动化或真实入口检查。
- **`P2`（次要展示/边缘格式）**：聚焦轻核对，不机械套重型矩阵。
- **先红后绿 ATDD（Red Mode）**：`P0` 新行为和缺陷修复在修改业务代码前先把场景写成可执行测试并运行，观察其**精准失败在目标断言**（编译失败、语法错误或环境不可用不能充当证据），再写实现代码使其变绿。

同时要求设计与验收时，先固定预期再观察目标；预期有歧义时区分可验证项与待决项，新产品或相互依赖的产品决定交 `scd-discovery`。

## 与交付衔接

单独调用返回测试设计或验收报告，允许在隔离环境运行检查；已授权交付复用现有计划与 Issue 并由 QuickDev 写回，分开记录设计方案与实测结果。用于 QuickDev 独立验收时由新上下文验收者执行；分支、提交、发布、合并和关闭遵守 [QuickDev 发布契约](../scd-quickdev/references/release-contract.md)，涉及产品或持久测试代码变更沿用[计划确认契约](../scd-quickdev/references/planning-contract.md)。
