# 测试设计

## 把用户要求变成可验证场景

1. 查明这次交付要改变的行为，以及会受影响且已确认需保留的行为。用用户原始要求、正式产品或 UX 契约、获批计划和 Issue 互相核对。已有验收 ID 原样保留，新场景沿用仓库的命名约定。
2. 从需求检查是否有遗漏或缩小，再从拟定验收项检查是否有无来源的要求。来源冲突时写出冲突句子、影响和待决问题，保留可独立确认的场景。
3. 写出能重放的起始状态、动作和用户或调用者能观察的结果，并为每项标明 `风险级别`（`P0`/`P1`/`P2`）。优先使用真实入口。只补会改变验收结论的成功、失败或边界场景，避免无关排列组合。
4. 为关键场景明确一个能被识别的错误结果（独立反例），说明哪条断言或运行观察会拒绝这个结果。对于清晰小改动或 `P2` 场景，一条足以区分错误实现的聚焦轻核对即可。

### 风险级别分层（P0/P1/P2）

- **`P0`（核心契约、权限、数据一致性、不可逆路径）**：必须有独立反例、先红后绿 ATDD（Red Mode）与强制独立新上下文子 Agent 复跑；严禁使用 `WAIVED` 豁免。
- **`P1`（主要业务流程与失败恢复）**：常规验收矩阵与自动化或真实入口检查，覆盖核心成功、失败与恢复路径。
- **`P2`（次要展示/边缘格式）**：聚焦轻核对，用精简直接检查验证即可，不机械套重型矩阵。

| 验收 ID | 风险级别 | 要求及来源 | 起始状态与操作 | 预期结果 | 必须识别的错误 | 验证方式 |
| --- | --- | --- | --- | --- | --- | --- |
| A1 | P0 | 已批准计划要求用户主动建立会话 | 无会话时发送，再主动建立会话 | 第一步给出建立指引且会话数不变；第二步才产生一个会话 | 直接发送时悄悄新建并成功发送 | 经公开入口观察返回状态与会话数（先红后绿 ATDD + 独立复跑） |

需求尚待批准时将方案标为拟定，并指出需要确认的产品选择。批准后，用既有计划的精确 Git 版本引用验收预期。Issue 承接执行和证据。补充测试数据、定位器和等价观测允许保留同一预期；改变可见结果、约束或例外之前按原计划的确认规则处理。

## 先红后绿 ATDD（Red Mode）

- 针对 **`P0` 新行为与缺陷修复**，在修改业务代码前先把对应验收场景写成可执行测试并运行。
- 先观察该测试**精准失败在目标断言**（证明用例真正捕捉到缺失行为或缺陷），再编写最小实现代码使其变绿。
- **编译失败、语法错误、测试未执行或环境错误/不可用不能作为目标断言精准失败的 Red Mode 证据**。
- 对于必须保留的既有行为，必要时用隔离的已知错误候选或替代输出确认检查能拒绝它。

## 条件触发式 NFR 检查面（5 项按需启用）

以下 5 项非功能需求检查面**仅当变更触及对应领域时启用，不为无关小改强填**：

| NFR 检查面 | 触发条件（触及对应领域时启用） | 检查重点 |
| --- | --- | --- |
| 并发与幂等 | 变更触及写入、提交、状态流转或异步触发 | 检查重复点击、请求重试、并发写入下的幂等性与状态一致 |
| 越权反例 | 变更触及认证、权限校验、租户隔离或受限操作 | 检查越权读、越权写与角色/边界绕过均被明确拒绝 |
| 大输入/空输入与超时降级 | 变更触及外部输入、批处理、解析或外部服务调用 | 检查空输入、超大输入边界与上游超时/异常时的稳定降级 |
| 向后兼容与数据迁移回滚 | 变更触及共享接口、持久化格式、配置契约或数据迁移 | 检查旧数据/旧调用方兼容以及迁移失败的安全回滚路径 |
| 首屏或关键接口明显性能退化 | 变更触及首屏渲染、核心列表查询或高频关键接口 | 检查无明显首屏阻塞、N+1 查询或关键路径响应显著退化 |

## 选择与行为匹配的验证

- 复用项目已有命令和测试层。纯规则用单元测试，跨模块或状态持久化用集成测试；用户界面旅程实际操作应用，按 [QuickDev 页面验收](../../scd-quickdev/references/page-acceptance.md) 覆盖适用状态、视口和视觉基线。
- 测试替身放在独立依赖边界，保留要验证的真实接线。验证流式界面时，替换模型提供者即可。让第一段在余下回复前到达，分别观察中间状态和完成结果。
- 缺陷与 `P0` 新行为按上述先红后绿 ATDD（Red Mode）先在旧版本或改动前观察目标断言精准失败，再在候选版本验证通过；编译失败、测试未执行和环境不可用不能作为指定行为失败的证据。
- 复核实际断言和执行报告。测试名、覆盖率与测试数量可以帮助定位，结论取决于相关检查是否到达目标路径并观察到预期结果。
