# 独立验收

读取 [QuickDev 证据契约](../../scd-quickdev/references/evidence-contract.md)。QuickDev 交付还须执行 [独立验收与关闭规则](../../scd-quickdev/references/release-contract.md#独立验收)。

## Blind-First 两步独立验收（先盲验、后对账）

验收者必须严格按 **Blind-First（先盲验、后对账）两步顺序**独立得出结论，防止受实施者自检结论影响产生锚定偏误：

### 第一步（盲验）

1. 定位原始要求、获批验收场景矩阵（含 `P0`/`P1`/`P2` 风险级别）、可还原的批准依据与适用仓库说明。区分批准的需求版本、差异基准、候选代码版本和实际运行的构建，核对是否为用户需要验证的版本和环境。单独审查缺少历史依据时只判断已建立范围。
2. **第一步不得读取实施者的自检 `PASS` 结论或自评摘要**。验收者只凭「原始要求 + 获批验收场景矩阵 + 精确差异（diff）+ 运行入口/环境」检查交付是否越界、关键规则是否仍在，并对变动的测试执行下方 `test-review` 5 条测试反模式门禁；同时对照[工程最佳实践](../../scd-quickdev/references/engineering-practice.md) §4 检查是否命中 `code-review` 6 条结构反模式门禁。改变产品预期须有明确的新批准，现有候选测试通过不能证明改变合理。
3. 根据批准预期亲自执行关键检查并直接观察真实入口（页面变更按[页面验收](../../scd-quickdev/references/page-acceptance.md)实际操作对应版本与状态），**先独立形成逐项盲验结论**。若候选测试改变了预期或命中测试反模式，使用独立的可重放检查观察原要求，例如从公开入口调用后读取状态。

### 第二步（对账）

1. 在独立盲验逐项结论完成后，再对照 Issue 中的候选完成审计三本账（验收映射、实施任务账目、交付状态）逐项抓偏差。
2. 重点排查**实施者声称 `PASS` 但盲验未观察到**、**断言偏离原意图**、遗漏场景、跳过/零运行/无关测试或套件总数充数，以及实施任务或交付状态未闭合的缺口。
3. 发现实现偏差、证据缺口或无关基线故障时分别记录。实施者可以提供候选引用和环境操作指引，不能替验收者批准例外；需要环境或授权时，记录缺少的资源及所影响的验收项。

## `test-review` 5 条测试反模式门禁

验收者读取测试 diff 时必须固定排查以下 5 条反模式；命中任一条且导致关键行为未被真实观察时，不得采信该测试为有效直接证据，须改用独立可重放检查按原始预期复验（仍缺证或违背预期则判 `BLOCKED` 或 `FAIL`）：

1. **过度 Mock 穿透**：测试替身越过独立外部边界、架空被测真实接线或替掉被测逻辑本身，导致仅验证 Mock 预设；
2. **弱断言/浅断言**：如仅用 `toBeDefined`、`toBeTruthy`、判非空或宽泛匹配替代对精确状态、输出或错误语义的断言；
3. **测试实现细节**：把断言绑定在内部私有调用、内部实现结构或私有状态上，而非公开可观察行为；
4. **硬编码等待**：使用 `sleep`、`setTimeout` 等固定延时等待，导致测试脆弱抖动或掩盖异步竞态；
5. **无清理副作用**：测试残留共享可变状态、全局污染或残留文件，造成用例间顺序依赖或虚假通过。

## 证据与结论（含受控 `WAIVED` 出口）

- 每项保留验收 ID、预期、目标版本、命令与退出状态或实际操作、观察结果和证据位置。旧版本、旧构建或已改变范围的证据须重新验证受影响项。
- 验收页面时读取[页面验收](../../scd-quickdev/references/page-acceptance.md)，实际操作需要验证的版本和状态。看到输入控件只证明它存在；要证明发送与流式回复，需要从用户入口操作并观察相应结果。
- **机器门禁主结论保持 `PASS`、`FAIL` 或 `BLOCKED`**：一项已观察到的行为与批准预期矛盾就判 `FAIL`（同时存在缺证项时，仍单列其阻塞原因）。没有已确认的违背但一项必需行为无法验证（或存在违规豁免）时判 `BLOCKED`。所有 `P0` 与可测必需项都得到与目标匹配的直接证据、且任何单项豁免均符合下方受控 `WAIVED` 规则时才判 `PASS`。
- **受控人工豁免 `WAIVED`（仅限单项状态）**：严格限定**仅适用于非 `P0`、非高风险门**的外部环境或外部依赖暂时不可测项，且必须完整记录 **缺失原因、残留风险、补测/跟踪条件及用户显式批准依据**。**严禁对 `P0` 关键行为、高风险人工门或未获用户明示批准的缺口使用 `WAIVED`**；**严禁把已观察到的违背（`FAIL`）伪装成 `WAIVED`**；验收者不得替用户批准豁免，且仍不得把 `UNVERIFIED` 或部分验证行为提升为 `PASS`。
- 在报告末尾列出实际缺口、合法 `WAIVED` 项的残留风险与补测条件及复验条件。QuickDev 验收结果交给现有发布门，单独审查返回证据报告。验收过程中保持候选代码、已批准预期和外部交付状态不变。
