# SCD 需求发现

开始执行前必须先读取并遵守[步骤沟通](../scd-quickdev/references/step-communication.md)；直接调用本技能也适用。

在实施前解决重大产品决策，不把 Discovery 变成固定仪式。全新产品需定义已确认 MVP 基线；现有产品只覆盖下一项连贯交付。完整 Discovery 期间不得编辑实施代码，实施前用户必须明确确认合并契约。设计或实施前读[计划确认契约](../scd-quickdev/references/planning-contract.md)（只读查询/审计不建计划，保持更窄治理权限）。

## 选择最轻量且充分的路径

检查请求与仓库后内部择路（除非被问及方法，否则不公布路径名）：

- **清晰交付：** 结果、边界和可观察验收已清晰。无需完整Discovery访谈，交给遵守计划确认契约的 `scd-quickdev`。
- **单点澄清：** 一个答案即可使工作可执行，只问该实质问题后交接。
- **完整发现：** 多个相互依赖产品决策或高成本边界未决，走下方完整流程。

全新产品、应用、插件、服务和系统默认走完整 Discovery（确认后得轻量 PRD）。用户已提供完整 Issue 或产品契约时走就绪快速路径。若已确认结果需多个可独立验证交付，先稳定共享项目核心，再交给 `scd-project` 拆解，不得先创建一个过大的实施 Issue。

## 先调查，再提问

访谈前阅读仓库说明、现有 Issues、架构、测试和实施，不向用户索取可查到的环境事实；明确区分事实、决策、假设与延期项。前期用户、竞品或需求强度缺关键证据时先用 [scd-research](../scd-research/SKILL.md)（已有充分研究/批准规格或清晰局部变更不强制，用户固定形态或跳过时保留约束与风险）。Research 负责是否值得做，Discovery 负责具体做什么与契约确认；只要求研究时由 Research 独立结束。

## 确定交付切片

- 新产品开场先定主要用户、核心痛点与期望变化（对可疑方案假设质疑一次并给建议，用户固定形态后按约束推进）。
- 全新产品切分交付前先稳定 MVP：愿景、主要用户、痛点/替代、MVP 目标与非目标、核心旅程、稳定 `FR-*` 需求、规则/失败/数据/权限/集成、可衡量成功指标与待定项（不扩张为路线图或实施任务）。
- 需设计体验或视觉时在核心稳定后组合 `scd-uiux`，产品可见 UX 决策回到同一个合并契约中统一确认；建新系统或改边界/所有权/共享契约时组合 `scd-architecture`。此后 UIUX 与 Architecture 可以并行进行，但前后端独立实施前必须统一为一个共享的机器可读契约（清晰局部变更无需调用两者）。纯文本 Discovery 只收敛用户任务、信息范围与产品边界，不得用纯文字选项要求用户凭空拍板具体界面布局、视图数量或交互细节；若需在本阶段定案具体界面形态，必须先组合 `scd-uiux` 提供可渲染的交互原型供用户查看后再合并确认，否则将该界面形态显式留待 `scd-uiux` 阶段确认。

## 沿决策树按轮访谈与持久草稿

完整 Discovery 开始时阅读 `references/interviewing.md`。每轮一次性抛出整个前沿（前置已落定且互不依赖的未决决策），每题固定含编号、标题、为何现在重要、有实质差异的备选项及单行推荐答案，让用户按编号作答；先上游后下游，互赖题不同轮抛出；只展开实际触发分支。每轮重算前沿后给简短收敛摘要，不逐点讨确认；漏答保持待定，不以临时假设解锁依赖。

草稿与逐轮确认按共享计划契约保存按需文档并提交本地计划分支，`current.md` 仅作增量恢复索引。

## 审查就绪度并请求确认

宣布契约就绪前阅读 `references/readiness-review.md`。高影响分支闭合后静默审查就绪与矛盾，明确各验收的外部验证衔接点，检查已启用的 UIUX / Architecture / 共享契约及新产品 `FR-*` 唯一性与指标可观察性，展示紧凑共同理解摘要并请求一次明确确认（沉默、部分同意或自信均不算确认；修订后重审）。

## 持久化已确认契约并交接

写入仓库前阅读 `references/artifacts.md`：

1. **已确认的全新产品：** 从 `assets/product-prd.md` 创建/更新 `.scd/product/prd.md`（`status: approved`、实质变更递增 `version`、`approved_at`、稳定 `FR-*`），通过普通低风险文档路径确保可从默认分支访问（未进默认分支时阻塞下游）；将 PRD 作为产品基线权威来源。
2. **交付与交接：** 现有产品的清晰变更按任务计划管需求/版本，由明确确认的中文 GitHub Issue 管执行验收；全新产品由 PRD 管产品基线、Delivery Issue 引用路径/版本/`FR-*` 管切片；多交付项目把共享核心交给 `scd-project` 建 Initiative 与 DAG。跟踪器不可用时报告阻塞（不用 `.scd/specs/` 替代）。
3. **交接边界：** 仅讨论想法保留在对话；确认但不实施则清理临时状态并在建 Issue 后停止；确认实施则交 `scd-quickdev`。产品确认不替代架构、具体技术方案批准和开工授权。
