# 计划、确认与开工契约

## 适用边界

功能开发、缺陷修复、架构和交互设计、再工程及实际修复默认遵守本契约。纯状态查询、代码阅读和只读诊断不创建开发计划。Next只读展示批准版本、待确认项和可执行范围。Project只建立执行拓扑，不执行实现。Knowledge、Interview、Evolve保留显式调用、专用确认、私人存储及更窄写入边界；Evolve试验不授权提交、推送、PR或合并。

## 规模自适应分级（L0/L1/L2）

按任务规模和风险选择计划承载层级，避免局部小任务承受不必要的模板开销，同时保持全部确认底线：

- **L0（清晰局部小修/纯文档/小配置）**：范围局限在单点局部变更，无跨模块架构决策、公共/共享接口变更、数据模型或迁移影响，也不触及高风险人工门。**免建 6 模板 `.scd/plans/` 目录与双次本地计划提交**，由对话与紧凑中文 Issue 承载具体方案确认与开工授权（记录具体技术选择、受影响文件、用户实际确认依据、时间及开工范围）。**绝不得跳过用户对具体方案与开工范围的明确确认**，也不得扩大到含高风险门、跨模块架构决策或关键行为/UI 复杂度的任务；实施中若发现范围扩大，立即升级至 L1/L2 并暂停受影响工作重新确认。
- **L1（常规单功能/含关键行为或 UI 变更）**：保留 `.scd/plans/` 按需持久计划与精确 Git 版本批准，可只保留实际需要的计划文档（不生成空模板），并在后续提交追加批准事件。
- **L2（多交付 Initiative / 架构边界 / 高风险变更）**：保留完整持久计划目录、精确版本冻结、独立集成验收与高风险人工门。

无论 L0、L1 或 L2，具体技术选择逐项确认、漏答保持待定、方案批准与开工授权分别记录、普通“继续”不扩权、实质变化暂停重确认、真实时间戳与不补造历史批准等核心不变量始终有效。

## 先调查，再逐项确认

先只读调查事实，再分轮展示当前未决选择、具体影响、推荐及理由，每轮问题互不依赖。功能、交互、架构、依赖、数据模型、接口、模块组织和测试策略等具体技术选择均由用户确认，不以可逆、惯例或模型自信代选。

开发新功能涉及外部库、SDK、框架特性、CLI 或平台协议时，确认技术方案前必须先核对本地锁定版本（如 `package.json`/lockfile/`pyproject.toml` 等实际版本，升级大版本需单列确认），再优先查阅对应版本的最新官方文档或本地依赖类型源码，禁止凭记忆编造过时 API；离线或文档源不可达时须显式标为 `UNVERIFIED`。

漏答保持待定，不以临时假设或推荐解除依赖；可继续独立只读调查。已批准计划明确的操作不重复询问。完整方案统一确认可覆盖其中逐项展示的具体选择；部分回答只批准明确选择的部分。普通“继续”只延续已批准范围，不批准未展示方案、新图版本或计划修订。

## 持久文件与权威

L1/L2 使用 `.scd/plans/YYYYMMDD-HHMMSS-<任务名>/`，实际北京时间创建，同秒重名追加短序号。按需从 `../assets/planning/` 使用六份模板：plan.md为索引，requirements.md保存需求，architecture.md保存架构增量，ux.md保存体验增量，implementation.md保存文件、顺序、依赖、验证、交付和风险，decisions.md追加决策与事件。不要生成不适用的空文档；L1/L2 实际开发必须有实施计划。L0 免建 6 模板 `.scd/plans/` 目录，由对话与紧凑中文 Issue 承载具体方案、确认依据与开工范围。

计划负责方案与批准版本；Issue负责执行状态、任务处置、验收证据和交付，引用计划文件及Git版本（L0引用本Issue方案确认与开工授权记录），不独立改设计。保留现有PRD、系统架构、机器接口契约位置，引用精确版本并说明本次增量，实施验收后更新基线。冲突先解决并确认。

## Git与批准

文档状态使用draft、approved、superseded及整数version。ready只表示工程或语义就绪，不等于用户批准或开工授权。

L1/L2 待审阅内容先提交本地计划分支，展示精确文件、文档版本及完整Git SHA。批准后在后续提交追加事件，引用此前已存在的提交与精确文件清单，不能自引用。L0 免双次本地计划提交，开工前须在对话展示具体方案与受影响文件，取得用户明确确认与开工授权后写入紧凑中文 Issue。Git字段不能单独证明用户真实批准。

事件记录ID、类型、文件/版本、目标Git SHA（L0记紧凑Issue方案确认记录）、用户实际确认依据、occurred_at和recorded_at；开工授权还绑定任务或Issue范围。没有消息ID时保存简短原文及上下文，不编造链接。方案批准与开工授权分别记录；明确指向当前版本的“确认本方案并开始实施”可同时授予两者。

方案实质变化或出现未覆盖技术选择时，暂停受影响工作、展示差异及影响、询问确认；保留旧批准事件，L1/L2 受影响文档递增version回到draft，L0 更新对话与紧凑Issue方案确认状态。未变化决策可复用。管理记录追加或普通实施代码提交不自动使批准失效。

## 时间、保存与恢复

所有新记录使用Asia/Shanghai、精确到秒、ISO-8601的+08:00；文档包含created_at、updated_at、version、status。创建、修订、决策、批准、开工和完成均关联版本。Agent事件读取实际时钟；用户事件原始时间未知时occurred_at为空并说明原因，recorded_at为实际记录时间。不得回填假时间或提前写完成，提交时间不等于用户确认时间。

每轮已确认决定落盘并提交本地计划分支（L0同步记录到紧凑中文Issue）。长期需求、方案、决策和证据摘要纳入Git，用历史还原，不复制versions/vN目录。仅忽略 `.scd/tasks/current.md`、`.scd/cache/`、`.scd/logs/`；不忽略整个.scd，不批量删除或取消跟踪已有文件。消费者更宽忽略或不明临时位置先展示调整并确认。

current.md仅保存恢复增量，引用计划与Issue；清理前将有价值决定和证据写回持久记录。旧任务缺失计划或批准关联时，保留已有基线、Issue与提交，整理当前真实方案确认后恢复受影响开发，不补造历史批准、不批量迁移。

## 开工与合并前清单

- 所需文档齐全，实施计划具体（L0见对话与紧凑中文Issue），无影响实施的未决选择。
- 当前方案对应获批Git版本及文件清单（L0对应紧凑Issue方案确认记录），实际用户依据可追溯，明确开工授权覆盖本Issue。
- Issue引用一致，适用设计和接口就绪；ready与用户批准分别核对。
- 合并前复核实际差异与获批范围、变更重确认、时间真实性和三本账。
- 独立新上下文验收亲读批准依据、精确版本和差异，保留真实页面、高风险与更窄权限门。

以上仅技能指令与检查清单，不新增运行时校验器、Schema检查脚本、依赖或Hook。文本回归与受控情景不保证所有宿主/模型每次遵从。获批范围内连续完成开发、验证、独立验收及普通交付。

## 批准版本的持久可达性

交付和清理必须保证每个引用的获批计划版本、精确文件及批准记录在持久分支和新克隆中可还原，删除最后引用前先按仓库合并策略完成持久可达性核对：

- **普通 Merge 仓库**：普通merge保留计划提交历史；合并后核对获批SHA是默认分支祖先，并从独立新克隆用git show读取每个SHA:file。普通 Merge 模式下，最终树或等价diff相同不能替代中间批准历史；未通过核对时保持 `BLOCKED`，不删除最后引用，不得擅自创建tag、改仓库保护或以对象暂存在本地为长期证据。
- **仅允许 Squash Merge 的消费者仓库**：当仓库策略仅允许 Squash Merge（不保留中间计划提交历史）时，不要求中间计划 SHA 成为默认分支祖先，不再一律 `BLOCKED`。允许以**合并后默认分支上的持久计划文件与批准事件记录（含批准版本、用户实际确认依据及时间戳，或 L0 紧凑中文 Issue 批准记录）+ 已合并 PR 合并提交**作为持久可达性证据；从独立新克隆或合并后默认分支核对上述文件与记录存在且未缺失后即可放行并执行分支清理。若合并后默认分支缺失该持久计划文件或批准事件记录（或无法核对已合并 PR 合并提交，或 L0 紧凑 Issue 批准记录缺失），仍保持 `BLOCKED` 且不删除最后引用；同样不得擅自创建tag、改仓库保护或以对象暂存在本地为长期证据。
- **L0 紧凑 Issue 路径**：L0 免建 `.scd/plans/` 与双次本地计划提交，持久可达性核对紧凑中文 Issue 中记录的具体方案、用户实际确认依据、时间戳与开工授权范围完整存在，配合已合并 PR 合并提交与默认分支差异即可放行清理；记录缺失时保持 `BLOCKED`。
- **仅允许 Rebase Merge 或其他会丢失批准历史的策略**：若既无法通过普通 Merge 祖先核对，也不满足上述 Squash Merge 持久落地核对，停止受影响交付和清理，向用户展示保留方案及影响供确认；未取得保留方案确认或无法从新克隆恢复时保持 `BLOCKED`，不删除最后引用。
