# 体验契约

聚焦设计、产品体验、持久 UX 产物和就绪审查使用本参考。只覆盖已触发的关注点，不要用通用建议填满章节。

## 契约边界

UX 契约负责用户如何理解和操作已确认的产品行为：

- 旅程、导航、界面和信息层级；
- 可见状态、转换、反馈、预防和恢复；
- 内容行为和交互模式；
- 响应式、输入方式和无障碍要求；
- 功能特定的视觉方向或设计系统增量；
- 接口需求以及对产品验收的追溯。

它不负责产品范围、后端架构、传输模式、持久化、部署或生产前端实施。引用相应权威来源，不要复制。

## 产物策略

持久化后备位置：

```text
.scd/ux/<slug>.md
.scd/ux/<slug>/visuals/
.scd/ux/<slug>/prototype/  # 仅复杂交互需要
```

从 `assets/ux-contract.md` 开始。允许的状态：

- `draft`：一个或多个重要体验决策仍未确定；
- `ready`：就绪审查通过，剩余说明不会改变可见行为或验收。

使用 `sources` 链接作为依据的 GitHub Issue、设计系统、接口契约、研究或现有 UI。使用仓库相对路径或稳定 URL。关联的 GitHub Issue 负责产品确认；重大新页面、整体改版或高成本视觉方向还需要一次视觉交付确认，并尽量与 Discovery 的合并确认同时完成。

优先保留一份功能 UX 契约。共享视觉系统放在仓库现有设计系统位置；只有它被多个交付复用并独立变化时才拆分。

## 视觉交付清单

显式 UIUX 设计、重要新页面、重要用户流程或整体改版必须包含项目内可渲染视觉产物。每项使用稳定视觉 ID，并记录：

- 界面或组件族；
- 状态；
- 对应旅程或验收标识；
- 目标视口；
- 线框、低保真、高保真或原型等保真度；
- 仓库相对文件；
- 已检查状态以及它证明的决策。

响应式布局真实变化时至少覆盖代表性桌面和窄屏视口。多步骤、有状态或恢复性交互必须链接可点击或可运行的非生产原型。外部 Figma 或其他设计链接只能作为来源，不能替代项目内稳定导出。可编辑源适合保留时同时保留；前端交接至少必须能在无外部权限时查看稳定渲染结果。

重大新页面、整体改版或高成本视觉方向把确认标记为“需要”，确认前保持 `draft`。普通局部设计可以标记“不需要”。记录确认状态和证据，不保存隐藏推理。

设计确认和实现后确认是两个不同事实：设计确认决定方案是否可实施；实现后最终视觉确认决定真实页面是否符合需要人工判断的视觉目标。整体改版、高保真品牌表达，或布局、密度和视觉语言本身属于关键验收时，把实现后确认标记为“需要”；其他页面默认“不需要”。设计阶段只需确定该标记和理由，不要求尚未存在的生产页面提前确认。

## 旅程与界面闭合

明确参与者和具体目标。一个旅程应呈现：

1. 进入条件；
2. 编号的用户与系统步骤；
3. 决定性操作或理解点；
4. 成功反馈；
5. 适用的失败或恢复路径。

建立界面清单，把每个界面映射到至少一个旅程或验收项。然后双向检查：

- 每项需求都到达一个界面或有意的非 UI 结果；
- 每个界面都因一项已说明需求而存在；
- 导航允许用户进入、继续、恢复和离开旅程。

不要为了补齐表格而制造界面。缺失的产品决策返回 Discovery。

### 全局壳层与跨路由组件

界面清单必须明确覆盖跨路由全局组件——壳层、页头、页脚、主导航与移动导航、主题和共享横幅——而不只覆盖路由族界面。这些组件出现在每条路由上，却不属于任何单一路由族；只按路由族审计会让每个节点都把它们视为“范围外”，最终无人负责。

对每个全局组件，审计必须：

- 把它分配给负责其视觉处理的界面族；或
- 明确记录“无需变更”决策，并给出一句理由。

审计结果交给 `scd-project` 时，每个需要变更的全局组件必须出现在至少一个交付节点的范围内枚举中。“某个节点会顺手修复”不是有效分配。

## 状态与交互契约

对每个重要界面或可复用组件，只覆盖适用状态：

- 初始或冷启动；
- 加载或提交；
- 已填充或成功；
- 空数据或零数据；
- 验证失败；
- 权限拒绝；
- 依赖或服务失败；
- 部分成功；
- 离线或陈旧数据；
- 破坏性确认、取消、撤销或重试；
- 焦点、键盘、悬停、选中、禁用和忙碌行为。

用 `状态 + 操作 -> 下一状态 + 反馈` 记录转换。除非产品规则禁止，可恢复失败后保留用户输入。重复操作、陈旧响应、延迟完成和待处理期间导航确实可能发生时，必须明确处理。

## 响应式与无障碍底线

响应式 Web 工作应说明：

- 宽度缩小时的内容优先级；
- 重排、换行、溢出和密集数据行为；
- 指针、触控和键盘交互差异；
- 只在布局真实变化处规定断点行为；
- 窄屏上的模态框、抽屉、菜单、表格和表单行为。

无障碍行为必须可测试：

- 语义结构和无障碍名称；
- 键盘顺序、操作、退出和焦点返回；
- 可见焦点以及不只依赖颜色的状态提示；
- 错误关联、播报和恢复；
- 关键颜色组合的对比度目标；
- 减少动态效果与缩放/重排行为；
- 信息性媒体的替代文本或等价含义。

WCAG 术语能够澄清要求时可以使用，但不要把通用清单粘贴到每份契约中。

## 视觉与组件纪律

存在设计系统或组件来源时写明。只描述功能特定的新增或覆盖。组件契约应区分：

- 用途与允许场景；
- 内容与组成；
- 交互与状态行为；
- 视觉令牌或继承样式；
- 响应式与无障碍行为。

现有令牌或布局规则能够表达决策时，不要写一次性像素值。不要为一个功能创建完整设计系统。

## 工程衔接点

对每个界面列出：

- 显示的信息；
- 用户操作；
- UI 必须接收和区分的状态与错误；
- 适合模拟的代表性示例；
- 可用时列出现有共享契约操作标识。

未解决项标记为“接口需求”，不要假装是已定稿 API。前后端字段、操作、权限和错误语义继续由共享接口契约统一负责。

## 就绪审查

设置 `status: ready` 前验证：

- 来源路径可解析，已确认术语得到保留；
- 每个面向用户的验收行为都有 UX 覆盖；
- 每个设计界面映射回旅程或验收项；
- 适用的加载、空数据、失败、权限、部分成功和恢复状态明确；
- 跨界面的交互规则内部一致；
- 响应式和无障碍要求可观察；
- 重要 UIUX 工作的主要界面族、关键状态和已触发视口都有项目内可渲染视觉产物；
- 每项视觉产物具有稳定视觉 ID 和完整映射；
- 复杂交互存在可练习的非生产原型；
- 需要确认的视觉交付已经获得明确确认；
- 实现后最终视觉确认已明确标记为“需要”或“不需要”，并记录触发理由；
- 视觉参考与书面契约一致；
- 接口需求有稳定的共享契约引用或具名统一负责人；
- 没有待定决策会实质改变可见行为或验收。

任一项失败时，保持 `status: draft` 并报告确切阻塞。视觉产物与 UX 契约冲突时不得静默指定一方优先，必须统一后才能 `ready`。
