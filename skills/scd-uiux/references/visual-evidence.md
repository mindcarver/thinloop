# 视觉证据

创建或验证线框图、视觉稿或原型前阅读本参考。

## 根据决策风险选择保真度

| 情形 | 最小有效产物 |
|---|---|
| 清晰的文案、令牌、间距或局部组件增量 | 书面或标注的增量说明 |
| 显式 UIUX 设计、重要新页面、重要流程或整体改版 | 项目内可渲染的主要界面与关键状态视觉图 |
| 层级、导航、表单分组或响应式重排需要设计 | 低保真线框图及已触发视口 |
| 整体结构或层级存在多个待比较方案 | 先讨论结构与内容归属，再低保真线框（禁谈字体与颜色），确认后进入高保真 |
| 有状态交互、多步骤任务或恢复行为 | 可点击或可运行的轻量原型 |
| 品牌、视觉语言、数据密度或组件外观属于关键验收 | 高保真关键界面和状态 |

保真度不是项目状态。0 到 1 产品仍可能只需要线框图；聚焦改版也可能需要高保真。

## 两阶段保真度循环

重要新页面、重要流程或整体改版默认分两阶段推进：

1. 先讨论再画图：主操作是什么、移动端隐藏什么、信任信号放哪等硬问题在讨论中解决；把错误的东西画得更快没有价值。
2. 低保真只决结构与层级：布局、信息归属和分节顺序；禁止在此阶段争论字体与颜色，那属于高保真和浏览器复核阶段。
3. 低保真获得用户确认后即冻结为参考（并入既有设计确认机制，不另造审批），再进入高保真视觉稿与实施；后续调整按视觉 ID 迭代并记录原因。

清晰的局部变更按上表直接交付增量说明，不强制两阶段。

## 从环境中选择工具

用户已有设计来源时直接使用。否则选择成本最低且能让决策可评审的工具：

- 用图表或线框图表达结构；
- 用静态视觉稿比较视觉方案；
- 协作编辑重要时使用 Figma 或其他可编辑设计工具；
- 必须练习响应式行为或交互时使用本地 HTML 原型。

不强制指定供应商。不要仅为创建原型而加入生产框架。外部工具链接只能作为来源；前端需要使用的稳定渲染结果必须进入项目版本管理。

## 建立视觉 ID 与项目结构

每份保留视觉产物使用稳定 ID，例如 `UI-001`，并在 UX 契约中映射界面、状态、旅程或验收、视口、保真度和文件。没有现有设计工作区时使用：

```text
.scd/ux/<slug>/visuals/
.scd/ux/<slug>/prototype/
```

不要只交付一张“理想状态”大图。只覆盖已触发状态，但加载、空数据、错误、权限、部分成功或恢复会改变结构或操作时，必须提供对应视觉图或清晰标注。布局真实变化时至少保留代表性桌面和窄屏结果。

## 保持原型非生产

原型放在现有设计工作区，或 UX 产物旁明确的非生产位置。不要导入应用入口、生产构建或运行时依赖。使用有代表性且不敏感的样例数据。

原型可以演示行为，但不定义后端端点、安全、持久化或生产架构。

## 通过检查而非假设验证

视觉设计先按[页面视觉质量](visual-quality.md)保留基线并明确方向，生成或收到视觉产物后执行其八维、轮次和对比要求；本节只补充设计交接检查：

1. 在目标桌面和窄屏 Web 视口渲染或打开；
2. 按共用标准检查视觉质量及代表性状态；
3. 产物支持交互时练习交互路径；
4. 与 UX 契约和产品行为来源比较；
5. 记录观察到的缺口并修订产物与契约；二者冲突时保持 `draft`；
6. 从相关契约章节链接保留的产物。

文件存在或渲染命令成功，不代表视觉已经审查。

## 保留决策，不保留图库

只有视觉产物传达下游所需的布局、层级、行为或外观时才保留。说明每份保留产物证明什么。删除或明确标记已被取代的方案，避免前端在冲突参考之间自行选择。

视觉产物包含偶然或陈旧细节时，明确标注并修订，不得让前端猜测。视觉产物与 UX 契约冲突时同时更新二者，统一前不得标记 `ready`。

重大新页面、整体改版或高成本视觉方向必须向用户展示完整视觉交付与 UX 契约，并记录一次明确确认。普通局部设计也按计划契约确认具体选择，ready与批准分别记录。

同时在 UX 契约中决定实现后是否需要再次确认真实页面。整体改版、高保真品牌表达，或布局、密度和视觉语言本身属于主观关键验收时标记“需要”；普通页面标记“不需要”。QuickDev 负责生成按视觉 ID、状态和视口排列的设计与实际页面对照；需要确认时，用户确认前不得关闭 Delivery Issue。
